# baileys-rs

A Rust port in progress of [WhiskeySockets/Baileys](https://github.com/WhiskeySockets/Baileys), based on upstream commit `0af2386292907f7d9742d8d41f830d8c48208fa1` (7.0.0-rc14).

Currently provides the full generated WhatsApp protobuf model, JID helpers, binary stanza encoding/decoding, crypto primitives, the Noise handshake and encrypted framing, persistent authentication/key storage, connection/pairing protocol helpers, an async WebSocket connection, persistent Signal direct/group sessions, USync query protocols, and message envelope/payload decoding. This is not yet a usable WhatsApp messaging client: synchronization, automatic message processing, and remaining high-level socket APIs still need to be ported. See [PORT_STATUS.md](PORT_STATUS.md) for scope and validation.

```rust
use baileys_rs::binary::{BinaryNode, encode, decode};

let request = BinaryNode::new("iq")
    .attr("to", "s.whatsapp.net")
    .attr("type", "get")
    .attr("id", "ABC123");
let wire = encode(&request)?;
assert_eq!(decode(&wire)?, request);
# Ok::<(), baileys_rs::binary::Error>(())
```

Build and check:

```sh
cargo test
cargo clippy --all-targets -- -D warnings
cargo fmt --check
```

Protobuf bindings and token constants are generated at build time. The build includes a vendored protobuf compiler, so a separate `protoc` installation is unnecessary. The schema and token data are included locally; building does not require the upstream checkout or Node.

Regenerate the binary parity fixtures from the upstream checkout using Node with TypeScript stripping support (verified on Node 26):

```sh
node scripts/generate-binary-fixtures.mjs ../Baileys
```

These fixtures use fixed synthetic keys and a synthetic certificate authority. They verify compatibility with upstream code, not a live WhatsApp server. The Rust runtime has no JavaScript or WASM bridge dependency.

`messages` provides padded protobuf encoding, message IDs, addressing/envelope decoding, and direct/group payload decryption through persistent Signal repositories. `Socket::decrypt_message` accepts a received `Event::Node` and runs storage/crypto on a blocking executor. Process each message stanza once and in arrival order: decryption consumes Signal counters. The result separates runtime key metadata from `proto::WebMessageInfo`, unwraps device-sent messages, combines multiple payloads with upstream's top-level replacement behavior, and retains ciphertext stubs and distribution failures. Encrypted PN envelopes learn LID mappings and migrate stored open sessions before decryption; mapping/migration diagnostics are returned separately. Automatic message events and receipts/retries remain pending. Rust rejects missing/invalid unsigned timestamps and retry counts; protobuf/crypto error diagnostics differ from JavaScript.

`relay` provides five-layer future-proof normalization, wire message/media classification, UTF-16-sorted participant hashes, DSM construction, signed device-identity encoding and unpadded newsletter encoding. Recipient fanout supports shared/per-recipient patch results, fresh padding, own PN/LID device DSM overrides, extra encrypted-node attributes and partial-failure diagnostics. An all-failed fanout returns status 500; empty recipient lists skip patching and encryption. `Socket::create_participant_nodes` runs configured fanout through persistent Signal sessions on a blocking executor. These successful encryptions consume counters; callers can assemble the participants/identity stanza and pass it to `send_node`. The socket relay operation integrates this default fanout; asynchronous patch hooks and automatic retries remain pending.

`reporting` selects protobuf fields using the upstream reporting table and derives version-2 HMAC report tokens, including nested fields and the source's Unicode HKDF-info encoding. It accepts the same padded bytes used by upstream relay; padding can make selection fail. Malformed negative lengths, excessive input and excessive nesting are rejected safely. `privacy::Repository` stores trusted-contact tokens with PN/LID resolution, preserves numeric/string timestamps and metadata, rejects stale replacements, builds token content, maintains the persisted index, and prunes expired records while retaining valid sender deduplication state. Mutations use SQLite transactions. `Socket::issue_privacy_tokens` sends the explicit issuance IQ; callers store its result through the repository. Socket relay attaches tokens and issues them asynchronously using server-prop gating and persisted sender deduplication. Notification/history token ingestion, automatic server-prop fetching and scheduled pruning remain pending.

`groups` parses group metadata, including PN/LID participants, owners, description revisions, community links, restrictions, membership approval and expiry. Missing/non-finite numeric attributes use `None`; a present invalid description/expiry number is represented by `Number(None)`. Socket helpers query metadata/participating groups, create/leave groups, update subject/description/participants, approve/reject join requests, manage invitation codes, revoke V4 invites and change group settings. Description updates fetch the previous revision before mutation. Participating-group queries emit `Event::GroupsUpdated`. V4 invite acceptance with buffered message updates, automatic dirty-group refresh/acknowledgement, group notification processing remain pending.

`relay::assemble` builds the encrypted message stanza from prepared cipher/participant nodes, including targeted retry addressing, peer-node flattening, device identity, reporting, expiry-checked privacy tokens and additional nodes in upstream order. `direct_recipients` splits own/other devices while retaining duplicates and excluding the exact sender. Retry helpers prefer existing LID sender keys, preserve the source's warning/fallback behavior, construct own-device DSMs and encrypt retry nodes with a count attribute. These are explicit preparation steps that consume cipher counters. `privacy::Repository::relay_token` suppresses expired tokens even when cleanup persistence fails. `Socket::relay_newsletter` sends unpadded plaintext through the newsletter early-return path. These helpers also power `Socket::relay_message`; asynchronous patch hooks remain pending.

`relay::Repository::transaction` resolves potential recipients before locking SQLite, then commits direct/group cipher state, retry distribution work, recipient memory and stanza preparation together. Its transaction handle implements the fanout encryptor and sender-key interfaces; use that handle for all store work inside the callback. `Transaction::group_fanout` encrypts a group payload and distributes its sender key to untracked devices, excluding hosted/99 devices and repeating distributions for status sends. It preserves upstream's marking of partial-failure recipients in sender-key memory. A failed batch discards its ciphertext and rolls back all key changes. Socket participant fanout now uses this batch transaction. This API commits prepared data before returning it to the caller.

`crypto` exposes AES-256 GCM (12-byte nonces, appended authentication tags), CTR, PKCS#7 CBC, IV-prefixed CBC, SHA-256, MD5, HMAC-SHA-256/512, HKDF-SHA-256, and pairing-code PBKDF2. `KeyPair` supports X25519 agreement and the deterministic Curve25519 signature format used by upstream's pinned libsignal backend. Private keys have redacted debug output and are zeroized when dropped. The MIT notice for the signature algorithm source is included in `licenses/curve25519-js.txt`.

`NoiseHandler` verifies the server certificate chain, produces the client static-key ciphertext, authenticates the handshake payload, and transitions to encrypted transport. The default certificate authority and protocol header match upstream. Synthetic peers can provide an explicit alternate authority through `noise::Config`. Feed websocket fragments with `push_bytes`, then pull one frame at a time with `next_frame`; this allows processing a server hello before a coalesced first encrypted stanza. All state mutation requires exclusive Rust access. Frame size and pending-buffer limits are bounded.

The Rust verifier checks the underlying libsignal verification result rather than mirroring the TypeScript wrapper's assumption that an invalid signature always throws. It rejects noncanonical/weak signatures and non-contributory X25519 agreement. Noise authentication failures terminate the handler; counter exhaustion never wraps a nonce, and transport initialization requires a verified server handshake. Certificate verification follows upstream's chain signatures and issuer serial checks; certificate expiry and leaf-to-static-key binding are not additional checks in this port. These are material behavior choices to review when integrating the client.

`connection` builds login/registration protobuf payloads, browser/companion identifiers, QR data, and pairing replies. `configure_successful_pairing` verifies the ADV HMAC and account signature for standard/hosted identities, signs the device identity, and returns the reply plus credential updates. Phone pairing helpers wrap the companion ephemeral key, process the primary response, encrypt the companion key bundle, and derive the ADV secret. Request/finish helpers expose deterministic-material variants for fixture verification; production wrappers generate fresh random material. Browser payloads and both pairing exchanges are checked against upstream bytes. The socket integrates these helpers with persistent credentials and connection events.

`socket::Socket::connect(config, store)` returns a handle and event receiver after the WebSocket/Noise handshake. Account login follows asynchronously; `wait_for_open` waits for initialization, while QR and phone pairing use `Event::Qr` and `request_pairing_code`. A single Tokio task owns the WebSocket and Noise state, routes IQ replies, handles keepalives, and persists credential changes through `spawn_blocking`. `query` generates IDs, reports stanza errors/timeouts, and removes pending queries when its future is dropped. Pending requests and event history are bounded; broadcast subscribers must handle lag. Dropping the last socket handle closes its task, and `close`/`logout` explicitly close the connection. Reconnect by calling `connect` again with the same store; automatic reconnection is left to the caller, as in upstream.

Login checks server prekey counts, uploads and acknowledges persisted batches, activates the connection, and requests the key digest. Upload failures retry with exponential backoff; a missing digest triggers another upload. Pair-success, routing information, and phone-pairing ADV-secret updates persist before subsequent protocol steps. The local mock peer exercises registration/login, both pairing methods, reconnect routing, queries, cancellation, prekey retries, QR rotation, and shutdown. This integration has no live-account validation. Signed-prekey rotation, server-driven low-prekey notifications and full initial synchronization still require implementation.

`signal::Address` maps PN/LID/hosted JIDs to upstream Signal addresses. `SenderKeyName` supplies the group storage name and UTF-16 hash. `signal::group::Repository` creates/processes sender-key distributions and encrypts/decrypts group payloads in SQLite transactions. Encryption returns the distribution captured before the ciphertext, matching upstream. Records use the actual JSON/BufferJSON format stored by Baileys, retain five states and up to 2,000 skipped message keys, and resume across process/database reopen. Private state is redacted in debug output and zeroized on drop. `SqliteAuthStore::transaction_with_error` permits protocol errors to roll back writes without losing their type. These operations are synchronous; async callers should use a blocking executor.

Group interoperability fixtures run the upstream TypeScript implementation against synthetic keys. Rust matches distribution bytes, signed AES-CBC ciphertext, chain/key-cache state, shuffled delivery, and the 2,000-message skip boundary. The pinned upstream cipher sends counters 0, 2, 4, ...; the Rust cipher preserves this behavior. Duplicate distribution IDs are appended and resolved using the oldest matching state, as upstream does. Rust rejects unsupported major versions, malformed records, and counter wraparound, and leaves state unchanged on authentication/decryption failure. Socket integration of direct/group messages remains unfinished.

`usync::Query` constructs queries for devices, contacts, statuses, disappearing mode, LIDs, usernames, and bot profiles. Typed result parsing preserves the current upstream dispatch rules and empty side list. Status/disappearing-mode times are Unix milliseconds in Rust. `extract_device_jids` applies own-device, zero-device, and key-index filtering, retaining upstream's hosted-domain propagation through a user's device list. `Socket::execute_usync`, `on_whatsapp`, and `fetch_lid_mappings` execute these queries over encrypted transport. Fixtures compare five exact query configurations and every built-in parser, including the upstream username bytes/string and nested bot-profile behavior.

`Socket::get_usync_devices` discovers relay devices through message-context devices/LID USync, stores mappings, attempts forced primary LID session refreshes, and persists device lists for migration. `Config::devices` configures a shared five-minute cache with a Rust capacity limit; `invalidate_user_devices` refreshes selected users. Explicit device JIDs bypass discovery/filtering. Cache hits retain the first fetch's zero/own-device filtering and use the user alone as the cache key, matching upstream. Empty extracted lists are not negative-cached. Session-refresh and device-list persistence failures are logged while discovered devices remain usable. Rust rejects malformed device JIDs and offers zero TTL/capacity to disable caching; custom external cache adapters and automatic device-notification invalidation remain pending.

`Socket::assert_sessions` deduplicates JIDs, validates existing sessions, resolves missing PN aliases with background LID USync, and requests missing or forced bundles with `reason="identity"`. Direct LIDs precede resolved PN aliases in the request. Unmapped PNs are omitted, preserving upstream's possible empty key request. `resolve_lid_mappings` exposes the same stored/network lookup. Key injection and database access run on blocking executors. Eight upstream discovery operations, five assertion request scenarios, cache boundary tests and an encrypted peer test verify discovery, mapping, refresh failures, forced requests, persistence and cache invalidation.

`signal::wire` parses encrypt-IQ and retry-receipt prekey bundles and constructs session-key requests. `Socket::establish_sessions` fetches bundles and injects them on a blocking executor. The local encrypted peer verifies contact/LID queries and persisted session establishment. Malformed key sizes/integer widths/signatures are rejected explicitly; per-user stanza errors retain their status codes. Device discovery/caching and automatic relay session assertions are integrated. Automatic retry requests, custom USync protocols and automatic receive integration remain pending.

`signal::direct::Repository` injects signed prekey bundles, encrypts direct messages as `pkmsg`/`msg`, decrypts replies and delayed messages, reports session information, and deletes explicit session addresses. It resolves PN addresses through the mapping store and persists the actual libsignal-node v1 JSON record format. Cipher operations commit ratchet state, incoming identity updates, and one-time prekey deletion together; failed authentication leaves them unchanged. Incoming identity changes re-establish the session, matching the upstream trust policy. The implementation uses the [X3DH](https://signal.org/docs/specifications/x3dh/) and [Double Ratchet](https://signal.org/docs/specifications/doubleratchet/) specifications and synthetic runtime fixtures; no libsignal implementation source or JavaScript runtime is included in the Rust client.

Direct-message fixtures verify exact ciphertext and session state through 12 bidirectional messages with multiple DH ratchets and delayed delivery, plus an exchange without a one-time prekey. Five Rust tests cover those fixtures, invalid signed bundles, failed MAC rollback, replay, PN/LID-aware persistent records and prekey consumption, and concurrent encryption without counter reuse. Deterministic-key/RNG variants support fixture verification; production methods generate fresh keys. Owned private state is redacted and zeroized on drop. Rust bounds message sizes, sessions and cached skipped keys, rejects corrupt/unknown session layouts, and includes incoming identity updates in the cipher transaction rather than persisting them before authentication. Complete archive/retry behavior, signed-prekey history, and automatic socket messaging processing still need work.

`signal::direct::Repository::migrate_session` performs device-list-driven PN to LID migration in one transaction, reports migrated/skipped/total counts, overwrites destination sessions, leaves identity keys in place, and moves only open sessions. Clones share a three-day migration cache (lookups do not extend its expiry); Rust adds a configurable capacity limit. `close` clears both migration and mapping caches. The source's missing-device-list and hosted discovery/address-validation quirks are retained: the requested device is appended only to the local plan, initial discovery uses `user.device` even for hosted users, and device 99 requires a hosted destination. Envelope learning stores mappings before attempting migration, preserving source behavior on migration failure. Rust validates stored device IDs as unsigned 16-bit integers. Ten upstream migration scenarios and native rollback/concurrency/cache tests verify this behavior.

`signal::mapping::Store` persists bidirectional PN/LID mappings, preserves device IDs, batches missing mappings through a supplied `Resolver`, and resolves PN Signal addresses to LID addresses. Clones share a cache with a sliding three-day TTL and configurable capacity. Concurrent requests with the same sorted, deduplicated JID set share a lookup, including empty/error results; resolver unwinding releases followers. Writes update caches after database success. `close` clears caches while retaining stored mappings; external writers require this invalidation. The API is synchronous and should run on a blocking executor when used from async code. The socket saves its own mapping and device list during successful login and migrates its own open session. As upstream does, failures in this own-account maintenance are logged without closing the connection.

Mapping fixtures cover 18 upstream operations. The port retains upstream quirks: reversed PN/LID fields are accepted without being swapped, remapping retains older reverse records, reverse lookup emits device `:0` and excludes hosted LIDs, and provider results reconstruct canonical device JIDs. Unexpected provider PNs are ignored rather than causing an iteration error. Rust uses an empty vector for upstream's absent batch result, and adds cache capacity/disable controls.

`auth::Credentials::generate` creates noise/pairing/identity keys, a signed prekey, the ADV secret, and upstream credential defaults. The current source's registration generator samples the first random byte; the port preserves that behavior while accepting valid imported 14-bit IDs. `me_id` returns a structured 401 error before authentication. Credential debug output omits keys and account data.

`auth::SqliteAuthStore::open(folder)` initializes or resumes `auth.sqlite3`. The `KeyStore` trait exposes all ten upstream key categories, atomic batch writes, deletion, and clearing keys while retaining credentials. `transaction` provides atomic credential/key updates, read-your-writes, a per-transaction read cache, and nested work using the same transaction. SQLite handles cross-process database locking and recovery; operations are synchronous and should run on a blocking executor in an async client. The database uses FULL synchronization and a 30-second lock timeout. New auth directories/files use Unix permissions 0700/0600. Persistence is plaintext, like upstream's multi-file adapter.

Prekey generation preserves the unuploaded range. `AuthTransaction::allocate_prekeys` persists new keys and allocation counters together; `mark_prekeys_uploaded` advances the upload cursor after acknowledgement. Transactional deletion of prekeys requires loading the key first, matching upstream's prekey manager. Invalid or corrupt persisted credentials are reported rather than replaced with a new identity.

The optional `CachedKeyStore` has configurable TTL/capacity, caches missing keys, and updates its cache only after successful backend writes. It assumes exclusive ownership of its backend; writers outside the wrapper require `invalidate`. Database transactions expose explicit `AuthTransaction` methods rather than JavaScript's implicit async-local transaction context and retry queues.

`import_baileys_folder` and `export_baileys_folder` bridge the upstream JSON folder format using BufferJSON-compatible bytes and lossless protobufjs Long values. Export requires a new destination directory and detects filename collisions before writing. Baileys replaces `/` with `__` and `:` with `-`, so ambiguous import filenames require an explicit filename-to-ID map; export returns that map. Session records retain the actual opaque JSON representation returned by libsignal-node, whose runtime shape differs from its TypeScript byte-array declaration. Unknown credential/contact fields survive import/export. The interoperability test runs the actual upstream multi-file adapter against synthetic Rust output; it is optional so normal Rust tests do not require Node.

The Rust API uses `Option` for absent protobuf fields and an enum for node content. Attributes preserve insertion order because stanza fixtures must match upstream bytes. Decoding raw string content returns bytes, matching upstream. The decoder adds byte, node-count, nesting, and decompression limits, and rejects trailing bytes. `Jid::parse` rejects invalid numeric device/agent fields rather than representing JavaScript `NaN`. The binary encoder preserves upstream's one-byte companion-device encoding.

Upstream's protobufjs schema contains nonzero-first proto3 enums. The build generates a temporary schema with synthetic zero variants where required by `protoc`. Existing field numbers and enum discriminants remain unchanged. Bindings preserve 64-bit integers as Rust integers, without JavaScript number conversion. Synthetic enum variants are code-generation accommodations, not newly discovered WhatsApp protocol values.

MIT licensed. The upstream copyright notice is preserved in [LICENSE](LICENSE).

`Socket::relay_message(destination, message, RelayOptions)` discovers recipient devices, asserts sessions and prepares direct/group/status ciphertext, sender-key distributions, targeted retries, reporting and privacy-token nodes in one auth transaction. It handles newsletter plaintext and peer messages, uses provided or generated IDs, accepts cached group metadata/status recipients, and serializes relay operations per socket. The default patch is unchanged message content; asynchronous patch hooks remain pending. `ServerProps` defaults match upstream (privacy sending/photo flags enabled, LID issuance disabled); `apply_server_props` accepts numeric AB IDs or named flags, but automatic AB-property fetching is still pending.

Relay validates local stanza encoding before committing prepared cipher state, then sends through the transport without holding the SQLite lock. Local preparation errors roll back cipher state. Transport failures retain committed counters because delivery may be ambiguous; upstream instead sends inside its key-transaction callback and discards staged state on callback failure. This native durability choice avoids counter reuse and blocking socket auth persistence on a network-held database lock. Callers must handle failed delivery; there is no automatic retry queue yet. Privacy issuance runs after successful sends, deduplicates in-flight requests, stores the reply and records the sender timestamp; task failures are logged.

`Config::patch_message_before_sending` accepts a cloneable `relay::MessagePatch` callback returning a shared message or per-recipient payloads. Group payload calls receive `None`; newsletter calls receive an empty slice; reporting/direct/distribution calls receive recipient slices. Group payloads reject per-recipient results. Recipient patches can add targets with existing sessions; stored PN/LID aliases are resolved inside the auth transaction for those additional targets. Own-device DSM replacement follows upstream fanout rules. Reporting uses the patched shared message; per-recipient reporting results suppress tokens because upstream selects the wrapper rather than its nested message. Newsletter per-recipient results encode empty plaintext, matching upstream's array-as-protobuf-object behavior. The synchronous callback runs on a blocking worker and may run inside the key transaction: it must not access the same auth store or re-enter relay. Async callbacks and their network/storage coordination remain to be implemented.

`retry::Manager` implements the recent-message cache (512 messages, five-minute TTL), retry counters with sliding 15-minute TTL, hourly session-recreation decisions, retry reason parsing/MAC classification, base-key comparison cache (1,024 entries, 15-minute TTL), statistics and cancellable delayed phone requests. Clones share serialized state. `Config::enable_recent_message_cache` defaults to true and `max_msg_retry_count` to five; `Socket::message_retry_manager` exposes the optional shared manager. Successful relay caches the original message, including group/status/peer sends, while targeted retries and the newsletter early return skip insertion. Connection shutdown clears state and cancels pending phone requests. Automatic incoming retry receipt handling, explicit retry-request and phone-placeholder APIs are implemented.

The native manager purges expired entries on each operation rather than running upstream's cache autopurge timers; idle expired memory is retained until another operation or socket shutdown. Limits, recency, non-sliding recent/base TTLs, sliding counter TTLs and the source's duplicate-message-ID index disposal quirks are preserved. `with_clock` accepts a millisecond clock for deterministic testing; zero cache start times preserve the LRU's special no-expiry behavior. Phone scheduling requires a Tokio runtime and a synchronous callback, which can spawn async work; callbacks execute after releasing state locks. Native retry counts and clock values are unsigned integers.

`receipts` aggregates incoming message keys into first-seen chat/participant groups, preserves duplicate IDs and builds delivery/read/played/history/peer/sender receipts and ACK/NACK stanzas. `Socket::send_receipt`, `send_receipts`, `read_messages` and `send_message_ack` expose these operations; `reject_call` sends the call-rejection query. Read receipts use current Unix seconds and choose `read` only when cached `readreceipts` is `all`, otherwise `read-self`. Sender receipts route PN/LID conversations to the participant, retaining the conversation as recipient. Missing protobuf key fields are retained and omitted from wire attributes as upstream does; empty ID lists return status 500. Native ACK error codes are unsigned 32-bit integers.

`privacy_settings` provides the settings query/parser and typed privacy values. Socket APIs fetch/cache settings and update messages, calls, last-seen, online, profile picture, status, read receipts and group-add policy. Updates leave the cached snapshot intact, matching upstream; use `fetch_privacy_settings(true)` to refresh it. Failed refreshes retain existing cached values. The parser accepts category name/config-code and value/config-value fallbacks and represents absent values as `None`. Automatic incoming receipt processing and receipt ACK dispatch are implemented; automatic message/notification processing and call events remain pending.

`Socket::send_retry_request` decodes an incoming message envelope, advances retry counters, suppresses/reset attempts at the configured limit, optionally recreates sessions and sends a retry receipt with registration/device identity and replacement keys. The default `enable_auto_session_recreation` is true. The actor prepares and persists a selected prekey plus both key cursors in one transaction, updates its credentials and emits `CredentialsUpdated` before transport send. Key-state preparation failures roll back; exposed state commits before I/O as in native relay. Counts and recreation checks occur before receipt preparation and remain consumed on later errors, matching the source's ordering. With the retry manager disabled, a one-hour counter cache and immediate phone-request fallback are used. Custom retry/placeholder cache adapters and automatic retry dispatch for failed incoming message decryption remain pending.

The first two retry attempts schedule a phone request after three seconds. `request_placeholder_resend` deduplicates requests by message ID, retains an optional `messages::Envelope` with original protobuf/runtime addressing metadata, waits two seconds and sends a placeholder PDO through `send_peer_data_operation_message`. Resolving an entry during that wait returns `RESOLVED` without sending. Entries otherwise expire eight seconds after that wait (with a one-hour cache TTL fallback). `has_pending_placeholder_resend` and `resolve_placeholder_resend` expose response/original-arrival handling; automatic response merging remains pending. Shutdown clears the native retry/placeholder caches; upstream closes its NodeCache timers. Placeholder expiry tasks hold weak references. Valid nonempty message IDs and native unsigned key/count widths are required.

Incoming receipts are processed by default (`Config::process_receipts`); `Event::MessagesUpdated` reports direct message status and `Event::MessageReceiptsUpdated` reports participant delivery/read timestamps. Raw node events remain available. Set `process_receipts` to false when calling `Socket::handle_receipt` manually. Processing is ordered in a separate worker, allowing async message lookup and session queries while the transport actor continues reading replies. Its internal queue is unbounded; slow lookups or offline bursts can grow the backlog. Offline event buffering remains pending.

Retries use the recent-message cache, then `Config::get_message` (`relay::MessageLookup`) for an async fallback outside auth transactions. They inject supplied bundles or force session queries, check registration/base keys, reset group recipient memory, preserve message IDs and enforce resend limits, including upstream's double increment for the first ID. Receipt ACKs are attempted after processing even when resending fails. Successful lookups mark retry success before sending, matching upstream. Targeted retry counts require finite unsigned 32-bit integers. Receipt timestamps retain upstream fractional, negative and non-finite number behavior through runtime `f64` fields.

`messages::generation` provides outgoing envelope construction (`from_content`), forwarding, disappearing-message settings, content-type selection and template/button extraction. `Options` controls the sender, message ID, timestamp, quote and expiration. Quotes normalize wrappers, retain only the selected quoted payload, remove its context, normalize its participant and preserve cross-chat addressing. Expiration is attached to the normalized payload, excluding protocol messages and newsletters; newsletters also omit quote context. Forwarding replaces existing context with forwarding metadata and converts conversations to extended text. Extraction supports buttons and both hydrated/plain four-row template forms.

Rust selects fields in protobuf schema order; JavaScript can additionally select by caller object insertion order. Typed content cannot retain runtime-only properties that the upstream protobuf encoder discards. Native generation consumes its input instead of mutating the caller's object, reports malformed content as typed errors, and uses unsigned timestamp/expiration widths. High-level non-media content generation is implemented below; native media preparation is implemented below; built-in link-preview fetching remains pending; socket send integration is implemented below.

`messages::generation::content` accepts typed `Content`, `Modifiers` and `ContentOptions`; `generate` additionally builds the outgoing envelope. Content covers text with optional link previews, contacts, location, reactions, deletion, forwarding, disappearing settings, invites, pin/unpin, both button replies, list replies, events, polls, albums, phone-number sharing/requests and sharing limits. Modifiers apply view-once wrapping, mentions, edits, context overlays and album association in upstream order. Reporting-eligible messages receive a fresh 32-byte secret; reaction/poll-update exclusions and nested/root secret placement match the source. Polls select the ordinary, V2 announcement-group or V3 single-select format and reject invalid selectable counts.

`ContentHooks` supports asynchronous link previews, invite thumbnail bytes and event call-link tokens, plus injectable clock/entropy methods. `DefaultContentHooks` uses the system clock and OS randomness and returns no enrichment. Preview failures are logged and suppressed; thumbnail/call-link failures propagate. `Preview::Disabled` suppresses lookup even for URL text. `PreparedMedia` applies the same modifiers to externally uploaded protobuf content; native upload, video-note and product preparation remain pending. Invite generation copies the group address/name, code, expiry and caption, then uses the thumbnail hook. Event input uses integer seconds rather than JavaScript dates. Poll counts are signed integers for validation; fractions are not represented.

`ContextPatch` replaces populated optional fields and nonempty lists; `clear_fields` represents explicit nulls/empty lists. The generator retains upstream insertion-order quirks: poll mentions/context target runtime-only metadata and disappear during encoding; view-once/edit wrappers also discard unsupported context. Text color strings use upstream's permissive hexadecimal prefix parsing; numeric colors are omitted because the pinned helper returns undefined. `extract_url` preserves its HTTPS-only expression, credential exclusion and JavaScript whitespace behavior.

`Socket::send_message` generates and relays content and returns its `WebMessageInfo`. It uses the saved sender identity, supports caller IDs/timestamps/quotes/expiration, status recipients and cached group metadata, and adds the upstream delete/edit/pin attributes or poll/event metadata with the same precedence. Group disappearing settings send a group-management IQ and return `None`. Other sends return `Some(message)` after successful transport submission. `send_metadata` exposes the attribute/node builder for explicit relay callers.

`Config::generation_hooks` supplies cloneable enrichment hooks; `SendOptions::hooks` overrides them per call. Hooks execute before relay, outside auth transactions, and can await socket queries.
